# Improved BM25: BM25F, plural folding, and supervised RSJ query weights

## Result

The best Kaggle score is **0.60761**, from BM25 v2 with review expansion. That file is the current final BM25 submission.

| Method (all search the full 50,000-product catalog) | Recall@1 | Recall@5 | Recall@10 | Kaggle |
| --- | ---: | ---: | ---: | ---: |
| Original BM25 (SQLite FTS5, 64 terms, binary) | 13.20% | 28.03% | 36.25% | 0.38120 |
| BM25 v2 (metadata only) | 27.65% | 47.60% | 57.83% | 0.57538 |
| **BM25 v2 + thresholded review expansion (final)** | 24.50% | 45.38% | 55.85% | **0.60761** |

Local scores are on the fixed 4,000-query validation partition (`artifacts/dev_split.json`). Kaggle scores are student-reported; the leaderboard partition was not specified. The validation partition was used only once, after every hyperparameter had been fixed.

## Leakage controls

- **Hyperparameters** were chosen on a *tuning slice*: 4,000 queries sampled with `random.Random(42)` from the 16,000 development-training queries. Statistics that use labels (RSJ weights, review index) were built from the remaining 12,000 queries when scoring this slice. Validation queries were never used for any choice.
- **Validation run**: RSJ weights (and the optional review index) use only the 16,000 development-training queries. Validation reviews are used only as queries; validation targets only to compute metrics. The development split groups by product, so no validation product has labelled reviews.
- **Test run**: RSJ weights and the optional review index use all 20,000 `train_gold.json` queries. Test reviews are used only as queries.
- The catalog index contains product metadata only. Category labels are not used anywhere.

## Method

1. **Preprocessing**: the original NFKC/HTML/media cleanup and ASCII alphanumeric tokenization, plus conservative plural folding (`curtains`→`curtain`, `batteries`→`battery`, `boxes`→`box`). Tokens containing digits are never changed. No external dictionary is used.
2. **BM25F** over title, store, features, and description. Each field's term frequency is length-normalized with `b=1.0`, weighted 5 / 1 / 1 / 0.5, summed, and saturated once with `k1=2.5`. IDF is `log(1 + (N-df+0.5)/(df+0.5))`.
3. **Query from all five reviews**: the reviews are pooled, and each catalog term gets query weight `(1 + log tf) * RSJ(term)^0.75`. Only the 128 highest-weighted terms are kept.
4. **Supervised RSJ term weights**: for each term, among labelled training queries whose reviews mention it, `p` = the fraction whose correct product's metadata also contains it. A Beta prior of strength 10 is centered on the pooled rate. `q` = df/N. The weight is `max(0, log[p(1-q) / (q(1-p))])`, the Robertson–Spärck Jones relevance weight. It learns that words such as *curtain* or *mirror* in reviews tend to appear in the product text, while sentiment words such as *love* or *great* do not. This replaces the hand-set 20% document-frequency stopword filter.
5. Ranking returns the top 10 products; ties go to the lower item ID.

Not helpful on the tuning slice: binary query frequency with RSJ (−2.7 points), higher RSJ power (2 or 3), heavier title weights, and a 64-term cap.

## Review expansion: local evidence versus Kaggle

The test set appears to share products with `train_gold.json`. Among confident test predictions, which are ~90% precise on validation, 45–48% of top-1 products are labelled training products. In validation errors the rate is 1.5–15%. So roughly half of the test products probably have five labelled training reviews. The variant `--review-expansion` builds a second BM25 index over those reviews. It adds `0.3 * max(0, z_review - 6)` to the metadata z-score, so only review matches that stand out from the review index count.

This variant cannot be validated directly. Every training product appears in exactly one query, and validation products are disjoint from development-training products by design. The two available estimates:

- Validation (products without labelled reviews): **−1.98 points** (57.83% → 55.85%). This is the cost of the bonus when the product has no labelled reviews.
- Proxy: half of the validation products receive 2 of their own reviews in the index, and every query uses the other 3. With expansion, the expanded half goes 46.95% → 48.65% and the unexpanded half 47.70% → 46.20%. Overall: 47.33% → 47.43%.

The proxy is weaker than the real test condition (3 vs 2 reviews instead of 5 vs 5), so its gain is probably underestimated. Local evidence alone could not justify the variant, so both files were submitted. On Kaggle, expansion improved Recall@10 from 0.57538 to 0.60761 (+3.2 points). This agrees with the estimate that about half of the test products have labelled training reviews. The two submissions differ only in the expansion flag; all expansion hyperparameters were fixed on the tuning slice before submission. The choice between the two files used the Kaggle score, because local validation cannot represent products with labelled reviews. The default CLI run still produces the metadata-only model; the runner script produces the final expansion file.

## Reproduction

```bash
pip install -r requirements-fast.txt   # NumPy only
python scripts/run_bm25_v2.py --predict-test --student-id 2024320020 --workers 8
python scripts/run_bm25_v2.py --predict-test --student-id 2024320020 --workers 8 --review-expansion   # optional variant
```

Or run `bash run_bm25_v2.sh 2024320020 8`, which produces both files; the final submission is `outputs/bm25_v2_expansion/2024320020_final.csv`. Outputs go to `outputs/bm25_v2/` and `outputs/bm25_v2_expansion/`, each with `metrics.json`, validation predictions, and `2024320020_final.csv`. The run is deterministic: there is no random sampling except the fixed-seed proxy split, and ties are broken by item ID. One run takes about 6 minutes with 12 workers. SciPy and `numpy.random` are not used, because the recorded Windows environment's application-control policy blocks their DLLs.
